- [x] ~~Rename `spawn_character_visual_when_ready` and drop its dead fallback.~~ Also 2026-10-26, while touching the same function for the state work above. It no longer spawns anything - that was a fallback for when `spawn_character` could produce a `Character` with no visual, parenting the mesh under it via `with_children`. With `spawn_character` deleted, that branch was unreachable *and* a landmine: it would have silently hit the exact `GlobalTransform`-under-a-`RigidBody` bug `sync_character_visual_transform` exists to work around. - [x] ~~Split `Loading` into `Loading`/`Initialize`.~~ Also 2026-10-26, refining the entry above same-day - see [[15 State Management]] for the full shape. `GameState` is now `Loading` → `Initialize` → `Playing`, not two states - because "wait for an asset handle to finish loading" and "wait for an entity to be spawned with a component" are different kinds of fact, and only the first has a completion *event* (`AssetEvent::LoadedWithDependencies`) to react to. Splitting them apart let `build_character_animation_graph` move into `OnEnter(Initialize)` and drop its readiness guard entirely - entering `Initialize` already proves the assets are loaded, so there's nothing left to check. The entity-level wait (`Character` existing, `AnimationPlayer` appearing) couldn't be collapsed the same way no matter how the states are sliced - `check_character_ready` still polls a plain query every `Initialize` frame, because there's no event for "this entity now exists" to subscribe to instead. Confirmed via a throwaway log that `Loading`→`Initialize`→`Playing` fire in order, each exactly once.

Added 2026-10-27, after trying (and reverting) a simplification of the Loading/Initialize state work above:

- [x] ~~Try collapsing `Loading` into a blocking `Startup` load.~~ Attempted and reverted same day - see [[15 State Management]] for the full "dead end" writeup. `bevy::tasks::block_on(asset_server.wait_for_asset(&handle))` from inside a `Startup` system deadlocks every time: the system that finalizes a background load into `Assets<T>` runs in `PreUpdate`, which can't start until `Startup` returns - confirmed hung 45+ seconds, not just slow, before reverting cleanly back to the three-state `Loading`/`Initialize`/`Playing` design (re-verified: both transitions still fire exactly once, in order). Worth remembering next time blocking-on-an-asset looks tempting: it's only safe from a genuinely separate thread (e.g. `AsyncComputeTaskPool`), never from inside the schedule itself.

Added 2026-10-28, applying the `asset/multi_asset_sync.rs` pattern to asset loading (see [[06 Assets and Scenes]] for the mechanics, both caveats, and how each was verified):

- [x] ~~Replace the `AssetEvent`-accumulating readiness check with an `AssetBarrier`.~~ Done 2026-10-28. `resources::AssetBarrier`/`AssetBarrierGuard` (an `Arc<AtomicU32>`, i.e. the sync half of bevy's own barrier example - no `event_listener`, no `AsyncComputeTaskPool`) replaces the `MessageReader<AssetEvent<Gltf>>` + `Local<HashSet<AssetId<Gltf>>>` accumulation. `load_character_gltf_handles` tags all 4 glTF loads with clones of one guard via `load_builder().with_guard(..)`; `check_character_assets_loaded` collapsed from ~20 lines of event-draining and id-matching to a single `barrier.is_ready()`.
  - **The real win is failure handling, not brevity.** `LoadedWithDependencies` only fires on success, so the old version left the game wedged in `Loading` forever on a missing/corrupt asset file. The guard drops either way (`bevy_asset`'s `spawn_load_task` calls `drop(guard)` unconditionally after logging any error) - verified by temporarily adding a deliberately-bogus guarded load: barrier still released, `Loading`→`Initialize`→`Playing` still advanced, and the failure surfaced as a clear `ERROR ... Path not found: ...` instead of silence.
  - Checked the one race this pattern *could* have introduced before committing to it: `is_ready()` flips on the IO thread as soon as the load task ends, but `Assets<T>` is only populated later in `PreUpdate`. Safe here purely because of schedule order (`StateTransition` is installed `insert_after(PreUpdate, ..)`, so an `OnEnter` can't observe the transition until after a `PreUpdate` has run) - would *not* be safe if the asset were read from the same `Update` as the check. Re-verified across 5 consecutive runs: both transitions fire exactly once, no panic from `build_character_animation_graph`'s `.expect(..)`.
